# 公众号排版，别再手调样式了

写公众号最耗时的环节，往往不是写字，而是写完之后的「收拾」：挑颜色、调行距、找封面、检查半角标点，然后把内容一段段搬进后台。同一篇 2500 字的文章，这套收拾动作可能要花三十分钟，而且每篇都要重来一遍。

## 耗时去哪了：每次都在重新做决策

排版慢的根本原因不是操作复杂，而是**每篇都在重新决策**：正文用多大的字？段落之间留多少空？强调色用绿还是蓝？决策一次的成本不高，但每周两篇、一年一百次，就是一百次重复决策。

更麻烦的是，这些决策还会互相打架。上一篇用 15px 正文配 1.6 行距，这一篇换成 17px 配 1.9，读者感受不到「精心设计」，只会觉得这个号不稳定。

## 把决策提前：一次配置，长期复用

解法并不新鲜：**把排版规则固化成配置，把重复动作固化成脚本**。本文配套的流程把这句话落到了六个环节上，每个环节都有人在关键节点拍板，机器只负责执行确定性的部分。

- 选题共创：把读者问题、一手经验、外部调研记录成素材库条目，选题卡必须写明人群、结论和独特证据，不立项就没有稿子。
- 大纲：按文章类型选模板，先确认结构再写正文，避免写完才发现论证缺一条。
- 成文：前端定稿，数据必须能追溯到素材库编号。
- 排版规范：字号、行高、字号梯度、配色都有明确区间，主题写成配置文件。
- 配图规范：封面与正文图的数量、尺寸、版权要求写清楚，图片用相对路径引用。
- 发布前检查：标题、摘要、字数、封面、图片、敏感词、标点、占位符全部脚本化，阻断项清零才允许发布。

## 机器能做的和机器不该做的

这套流程里，脚本负责的是**确定性的事**：把 Markdown 转成能粘进公众号的 HTML、检查图片文件是否存在、数标题有几个字、找出还没删掉的「待补」。这些检查每次运行结果一致，比人眼可靠。

脚本不该做的也很明确：发布。群发是不可逆动作，退订号一天只能群发一次，点错就没法撤回。所以脚本停在「粘贴即可」这一步，后面所有操作都由人在公众号后台完成并确认。

## 谁该用这套流程

不是所有人都需要。一个人一个月发一篇、从来不觉得排版烦，那继续手排就好。

真正适合这套流程的是**每周要发两篇以上**的账号，或者多人协作、需要交接的团队：因为重复次数足够多，一次配置省下来的时间才有意义；因为参与的人不止一个，规则写下来才有用。

这类账号的痛点是可预测的：时间被排版吃掉、风格每篇都不一样、发布前总会漏掉一两个细节。下面这张表把每个环节的产物和人工确认点摆在一起，你可以对照自己现在缺哪一块。

## 有人会说：这不就是又一个排版工具吗

不是。排版工具解决的是「Markdown 长什么样」，流程解决的是「写完一篇要经过哪些关卡」。前者换一个工具就重来一遍，后者沉淀在仓库里，下次直接复用，还能被 review、被迭代。

如果你也在为每篇稿子的「收拾」发愁，建议先做一件事：把这篇的处理清单存下来，下次排版前照着过一遍。

## 附：一张表看清每个环节的产物

| 环节 | 产物 | 人工确认点 |
|:---|:---|:---|
| 选题共创 | 选题卡、素材条目 | 是否立项 |
| 大纲 | 大纲文档、模板正文骨架 | 标题与结构 |
| 成文 | 定稿 Markdown | 事实核查 |
| 排版规范 | HTML 片段、预览页 | 预览观感 |
| 配图规范 | 封面与正文配图 | 选图与版权 |
| 发布前检查 | 检查报告 | 阻断项清零 |

最需要提醒的一点是：表格里的「人工确认点」不是多余步骤，而是这套流程里唯一能挡住返工和事故的地方。建议你把这张表存下来，当作下一篇稿子的检查清单。
